# 真机延迟调校

本文只讲一件事：拿到眼镜后，怎么把「动作/音画延迟」调到合适，并留下可核对的证据。

## 1. 三个量，别混为一谈

| 量 | 含义 | 位置 | 谁受影响 |
| --- | --- | --- | --- |
| 音频起播偏移 | 从调用 play() 到真正听到声的时间 | `timing.audioOffsetMs` | 谱面起点（判定与画面一起等） |
| 显示偏移 | 从绘制完成到屏幕呈现的延迟 | `timing.displayOffsetMs` | **只影响画面**，判定与计分不变 |
| 动作检测延迟 | 真实动作到被判定命中的时间 | 由算法阈值决定 | 判定时间戳 |

三者中只有前两项是可配置的；第三项要改算法，不能靠补偿掩盖。

## 2. 音频起播偏移怎么量

默认 80ms 是工程估值，不是测量值。

1. 打开 `motionDiagnostics`，跑一局，导出研究日志；
2. 找 `state: playing` 那条里的 `chartOriginMs` 与 `audioStart`：`audioStart.commandMs` 是 seek+play 的同步耗时，`estimatedAudibleAtMs` 是当前补偿后的估计可听时刻；
3. 用另一台设备以 120fps 录制画面与声音，数首拍画面与首拍鼓点的帧差，换算成毫秒，与上面的估计对照；
4. 差值写回 `timing.audioOffsetMs`，重新跑一局确认。

判定窗仍是 90 / 180 / 400ms，**不要**用调宽窗口来掩盖偏移。

## 3. 显示偏移怎么用

只在「画面明显比声音晚、但判定已经准」时使用，方向要试：

- 画面晚（音符到判定线时声音已经过了）→ 取正值，提前绘制；
- 画面早 → 取负值。

范围 ±250ms，默认 0。它是渲染读时钟的偏移，不参与任何计分逻辑；如果调了它之后分数变化，说明改错了地方。

## 4. 帧率怎么核对

左上角帧率计（`motionDiagnostics` 开启时）会显示实际回调间隔、峰值和绘制耗时。预期：

- 常规对局 60fps；
- 开启录屏时允许降到 45fps，但不应该出现长时间低于 30fps 或整段卡住；
- 若持续低于 45fps，先看绘制耗时峰值，再考虑减少舞台装饰，而不是继续降帧。

## 5. 教程与恢复

- 教程没有录音，不应等待音频偏移；
- 暂停恢复会重新 seek+play，再按同一起播偏移接续谱面，恢复后的第一拍应与音乐对齐；
- 如果恢复后感觉「抢跑」，先核对日志里的 `resumeAtMs` 与实际听感。

## 6. 记录什么

每轮调校记录：设备型号、系统版本、Studio 版本、Commit、`audioOffsetMs` / `displayOffsetMs`、两轮 A/B 的 perfect 占比与主观感受。没有这些，下一轮就只能重来。
